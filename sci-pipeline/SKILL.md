# sci-pipeline — 게이트를 강제하는 과학 파이프라인 절차

이 스킬은 문서를 만드는 도구가 아니다. **결과를 보기 전에 결정할 것을 결정하게 하고, 결정이 없으면 멈추게 하는 얇은 절차**다.
근거는 세 연구 프로젝트에서 실제로 되돌린 사고(`references/incidents.md`)와 공개 체크리스트(REFORMS, Kapoor & Narayanan 누수 분류, TRIPOD+AI 등 — `references/sources.md`)다.

## 0. 시작할 때 (모든 모드 공통)

1. 레포의 `AGENTS.md` → `CLAUDE.md` → `HANDOFF.md` 순으로 읽고 `git status`·`git worktree list`를 본다. 레포 규칙이 이 스킬보다 우선한다.
2. 연구 모드를 **하나** 선언한다: `EXPLORATORY`(결과를 보며 패턴·가설 형성, 전부 탐색으로 표기) / `CONFIRMATORY`(동결 카드를 결과 미사용 자료로 검정) / `REPLICATION`(선행 주장을 명시된 계약으로 재현). 탐색을 확인처럼 쓰지 않는다.
3. 모든 상태 주장에 **측정 시점과 증거 파일**을 붙인다. 문서에 적힌 상태는 주장이고, 지금 실행·조회한 결과가 사실이다.
4. 이번 턴에 다루는 **단일 질문**과, 결과가 어떤 명제를 유지·축소·보류·종결하는지 먼저 적는다(채팅에만, 파일로 만들지 않는다).

## 1. 모드

| 모드 | 언제 | 하는 일 | 새 파일 상한 |
|---|---|---|---|
| `design` | 새 파이프라인·새 실험 단계 | 게이트 G1→G5를 순서대로 통과. **카드가 동결되기 전에 구현 코드를 쓰지 않는다** | 카드 1 + 자료 계약 1 (같은 역할 파일이 있으면 그것을 고친다) |
| `implement` | 동결 카드가 있을 때 | G6 고정구 먼저(TDD) → 구현 → G7 기록 → 독립 리뷰 | 테스트·소스만 |
| `audit` | 기존 레포 점검 | 9개 게이트를 PASS/FAIL/UNSET/미확인/N/A로 판정(UNSET=아직 결정 안 됨, 미확인=실행·검증 못 함), 근거 `파일:줄` | **0** (결과는 채팅 또는 기존 HANDOFF·register에 추가 제안) |

공통 금지: 공통 프레임워크·패키지·KG·플랫폼을 먼저 만들지 않는다. 아이디어 여러 개를 섞지 않는다 — 한 번에 한 요소만 바꾼다.

## 2. 게이트 9개

각 게이트의 점검 항목·출처·실패 예시는 `references/gates.md`. 여기에는 통과 조건만 둔다.

| # | 게이트 | 통과 조건 (한 줄) |
|---|---|---|
| G1 | 목표·추정량 | 1차 질문 1개, 추정량·독립 단위·기준선 정의. 성과는 **기준선 대비 증분**으로만. 확장 과제가 1차 과제를 대체하지 않음 |
| G2 | 자료 계약 | 스키마·식별자 정규화·범주 표기·결측 부호·시각/시간대·순서 키가 명시되고, 위반 시 **halt**(자동 교정 금지). 실자료가 없을 때 합성·자리표시 자료로 **조용히 대체하지 않음** |
| G3 | 분할·누수 | 참가자(필요하면 가족·기관) 단위 분할, 전처리·특징 선택·튜닝 **전부 fold 안**, 미래 정보 차단, 분할 간 중복 점검 실행 |
| G4 | 봉인 확인 분할 | 확인 자료는 사전등록 후 **한 번** 연다. 저장소에는 해시만. 본 적 있으면 burned로 기록, 오염 의심 즉시 보고 |
| G5 | 동결 카드 | 바꾸는 요소 1개, 주지표·최소 관심 효과·불확실성·다중성·결측·중단 규칙·seed·탐색 예산이 결과 전에 고정. 미정은 `UNSET`. sha256 동결. **프로토콜 커밋이 결과 커밋보다 먼저** |
| G6 | 합성 고정구 | 정답을 아는 입력(심은 효과 + 효과 0 + shuffle/erase 대조 + 손계산 값)을 **매개변수 여러 점**에서 회수. 합성 결과로 전망하지 않음. 실패하면 기준을 낮추지 않고 실패로 기록 |
| G7 | 실행 기록·환경 | config·code·input 해시, 실패 seed 포함 전체 run 장부, 평가 코드·테스트 해시 고정(에이전트 수정 시 FAIL), 실행 환경별 수치 동작 확인, 바뀌지 않은 실패를 재시도하지 않음 |
| G8 | 판정 분류 | keep / modify / stop / inconclusive / no_candidate. 실패 유형(구성 불가·측정 역량·방향·실용 효과 미달·정밀도 부족·누수·실행 무결성)을 구분. **소프트웨어 실패 ≠ 과학적 null**. null도 결과 |
| G9 | 상태 분리·주장 | 문서 / 합성 / 구현 / 실자료 효과 / 외부 재현 / 임상 효용을 별도 상태로. 수치는 PMID·DOI 또는 `[확인 필요]`. "최초" 금지. 정본은 코드, 문서는 코드와 대조. 작성자가 자기 게이트를 통과시키지 않음. "완료"에는 테스트 출력 첨부 |

게이트 통과 기록은 `assets/gate_record.template.json` 형식(필드만 빌려 레포의 기존 장부에 쓴다). **장부가 없으면 HANDOFF의 기존 표에 행을 추가하고, 새 장부 파일은 PI 승인 후에만 만든다.** **리뷰어 판정은 권고이고, 게이트 통과 결정은 사람(PI)이 한다.**

## 3. design 모드 절차

0. **핵심 목표 먼저**: 아이디어(노트·대화)의 핵심 목표를 한 문장으로 되말하고 PI에게 확인한다. 핵심 목표를 "확장"이나 "별도 카드"로 강등하지 않는다 — 범위를 줄여야 하면 핵심 목표 **안에서** 줄인다(예: 문항군 1개·모달리티 1개·horizon 1개). "한 번에 한 요소"는 비교 설계의 규칙이지 연구 목표를 바꾸는 규칙이 아니다.
1. G1: 1차 질문·추정량·독립 단위·기준선을 사용자와 확정. 사용자 답이 없으면 `UNSET`으로 두고 진행을 멈춘다.
   - 기준선에는 예측 시점에 이미 있는 값싼 정보(같은 사람의 과거 측정·행동 이력)를 넣는다. 그래야 "새 정보의 증분"이 중증도 재독해와 구분된다.
   - 순차·생성 모델이면 채점 대상을 나눠 정의한다: 정답 이력을 주는 joint 확률(teacher forcing), 주변분포 예측, 정답 없이 이어 쓰는 자유 생성. 부분 관측은 주변화, 검사 중단은 terminal 경로로 다룬다.
   - **PI 질문은 PI만 정할 수 있는 것**(목표·δ·주지표·봉인 여부·위험 수용)으로 줄인다. 자료 접근 가능성·형식은 묻지 말고 실측 과제로 돌린다.
   - 코호트·자료 규모 수치는 논문 **전문**을 읽고 쓰며, 건수(검사 수)와 사람 수를 구분하고, 논문 안의 수치 충돌도 기록한다.
2. G2: `assets/data_contract.template.md`의 항목을 레포의 기존 데이터 사전에 채운다(없을 때만 새 파일). 계약 검증 코드는 실패 시 예외를 던지는 형태로 설계한다(pandera·pydantic 또는 표준 라이브러리 검사).
3. G3·G4: 분할 단위와 봉인 방식을 정하고 `scripts/group_overlap_audit.py`로 검사 계획을 세운다.
4. G5: 전부 UNSET인 단계에서는 동결을 시도하지 않는다. `assets/experiment_card.template.json`을 복사해 채운다. 미정 값은 지어내지 않고 `UNSET` + `fixed_when`. **초안 동안은 자유롭게 고치고 동결은 한 번만** 한다: `_how_to_use` 키를 지운 뒤 확인 실험 직전 `python3 scripts/freeze_card.py freeze <card> --strict`(필수 필드가 UNSET이면 거부). 해시는 카드와 같은 커밋에 넣어 run 폴더 밖 고정점으로 삼고, run 때 `verify <card> --expect <커밋된 해시>`로 확인한다. `.sha256` 사이드카도 새 파일 상한에 포함된다(레포에 장부가 있으면 사이드카 대신 장부에 해시를 적는다).
5. 독립 리뷰(§6)를 받고, 사람의 G1–G5 승인 후 implement로 넘어간다.

## 4. implement 모드 절차

1. `freeze_card.py verify`로 카드가 동결 해시와 같은지 확인. 다르면 멈춘다.
2. G6 고정구를 **먼저** 쓴다(RED). 정답·통과 기준을 테스트와 함께 커밋한 뒤 구현(GREEN). 형식은 `ID / fixture·의도적 오류 / 통과 판정` 표(예: 2문항 joint 확률을 손으로 열거해 NLL을 대조, 같은 사람을 train·test에 배치하면 거부)로 쓴다.
3. 병렬 작업이면 작업마다 `ID / 소유 경로 / 입력 버전 / 산출물 / 완료 검사 / 실패 시 조치 / 리뷰어`를 정하고, 같은 파일을 두 작업이 동시에 고치지 않는다.
4. G7: 모든 run(실패 포함)을 장부에 남긴다. 평가 코드·테스트 해시를 run 기록에 넣는다.
5. 끝나면 전체 테스트 출력 원문을 첨부하고 독립 리뷰(§6)를 받는다. 테스트를 skip·완화·삭제해서 통과시키지 않는다. 요구사항→테스트→증거 표가 레포에 없을 때만 `assets/acceptance_matrix.template.md` 형식을 HANDOFF 안에 표로 넣는다(별도 파일 금지).

## 5. audit 모드 절차

1. 레포를 수정하지 않는다(`git status` 전후 동일해야 한다).
2. 게이트별로 코드·테스트·장부·HANDOFF를 읽고 PASS/FAIL/UNSET/미확인/N/A + 근거 `파일:줄` + Wrong-if-X(이 판정이 틀렸다면 무엇을 실행하면 드러나는가)를 적는다. 가능하면 직접 실행해 확인한다(테스트, `group_overlap_audit.py`, `freeze_card.py verify`).
3. 문서의 상태 주장과 실측이 어긋나면 그 차이 자체를 FAIL 근거로 적는다.
4. 결과는 채팅으로 낸다. 레포 반영은 기존 HANDOFF·register 항목 추가로 **제안**만 한다.

## 6. 독립 리뷰

- 리뷰 프롬프트 정본: `references/reviewer.md`. 형식은 **Critical Issues / Counter-Arguments / Wrong-if-X / Verdict** + 게이트별 판정.
- 리뷰어는 보고서가 아니라 **코드·로그·git diff·원출력**을 받는다. 작성자의 요약·세션 기록을 주지 않는다.
- Claude Code: `pipeline-reviewer` 서브에이전트. Write·Edit 도구가 없고, Bash로 파일을 쓰지 않는 것은 지시로만 막는다(기술적 차단 아님) — 리뷰 전후 `git status --porcelain`이 같은지 확인한다.
- Codex·Antigravity: 새 세션에서 `references/reviewer.md`를 프롬프트로 리뷰하거나 `trinity review "<지시>" --file <경로>`. **별도 교차검증 경로를 만들지 않는다.**
- 리뷰 횟수·동의율은 엄밀성의 증거가 아니다. 다중 모델이 수렴하지 않으면 합의로 쓰지 않는다.

## 7. 멈춤 조건 (어느 모드든)

다음이면 다음 단계로 가지 않고, 막힌 이유·가장 작은 다음 행동·풀리는 증거를 적고 멈춘다.
- 1차 질문·추정량·기준선 미정 / 연구 모드·결과 접근 이력 미선언
- 자료 계약 위반을 자동 교정해야만 진행 가능 / 실자료가 없어 합성으로 대체해야만 진행 가능
- 분할 단위·독립 단위 미정, 또는 fold 밖 적합이 남음
- 확인 자료가 열렸거나 오염 의심
- 결과에 의존하는 정의(지표·임계값·대상)가 아직 바뀔 수 있음
- 고정구 실패를 기준 완화로만 넘길 수 있음
- 요청된 주장이 증거 상태를 넘음
